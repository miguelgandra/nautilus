# nautilus developer guide

This is the durable handoff document for `nautilus`. It describes the package as it is implemented on
`main`, not an aspirational redesign. When this guide disagrees with executable code, tests, generated help,
or Git history, those sources are authoritative and this guide must be corrected in the same change.

Keep this document compact and current. Record durable contracts, scientific assumptions, known hazards,
and the validation needed to change them. Do not turn it into a chronological work log, session transcript,
or list of unverified audit leads; use Git commits and issues for those purposes.

## 1. Purpose and scope

`nautilus` is an R package for processing and analysing high-resolution archival biologging records. Its
primary data are deployment-level time series from tags carrying some combination of depth, temperature,
tri-axial acceleration, magnetometer, gyroscope, and paddle-wheel channels. It also integrates lower-rate
ancillary records such as Wildlife Computers positions and wet/dry events, plus onboard video.

The package provides four layers:

1. ingestion, metadata validation, deployment trimming, time regularisation, and sensor quality control;
2. sensor-frame resolution, magnetometer calibration, orientation, and kinematic derivation;
3. optional scientific analyses for dives, tail beats, behaviour features, diel phase, and movement tracks;
4. plotting, video review/annotation, summaries, provenance, and export to downstream models.

The package is pre-release (`0.1.0`). Backwards compatibility matters for saved tag objects and established
workflows, but correctness and explicit scientific uncertainty take priority over preserving a misleading
result.

## 3. Core object and metadata contract

The unit of processing is a deployment, not necessarily an animal. `id` identifies the deployment;
`animal_id` identifies the animal. Never silently substitute one for the other.

A `nautilus_tag` is an S3 subclass of `data.table` and `data.frame`. The sensor series remains directly
accessible as columns, while all package metadata lives in one exact attribute:

```r
attr(x, "nautilus", exact = TRUE)
```

The supported public accessors are `tagMetadata()` and `processingHistory()`. User documentation should
prefer them to direct attribute access. The metadata schema is constructed in `R/nautilus-class.R` and
currently contains:

- `id`, `animal_id`;
- `deployment`: site, coordinates, deployment/recovery/pop-up times, attachment information, magnetic
  declination, and heading reference;
- `tag`: model, type, package/logger identifiers, paddle-wheel flag, and documented axis configuration;
- `biometrics`: passive animal traits supplied through metadata roles;
- `sensors`: present/excluded channels, original and processed sampling rates, and timezone;
- `span`: record bounds and original row count;
- `calibration`: source-side calibration constants retained as provenance, not applied again;
- `ancillary`: positions, dry events, and other secondary records;
- `axis_mapping`: applied state, per-family transforms, determinant/handedness, dropped axes, and provenance;
- `mag_calibration`: proposed estimate, applied state and parameters, QC, status, and provenance;
- `processing`: append-only records of pipeline steps and settings.

Operations such as subset, merge, aggregation, and `rbindlist()` can strip attributes or class. Use
`.restoreMeta()` on the result. Use `.appendProcessing()` for provenance. Legacy flat attributes are migrated
by `.ensureMeta()`; do not add new flat attributes.

`data.table` mutates by reference. Public functions must not alter caller-owned objects during validation,
report-only execution, sorting, or metadata migration. Use the existing safe input path or make an explicit
copy before mutation.

## 4. Input, output, and batch contracts

Most deployment-level functions use `.resolveInput()` and accept:

- a character vector of `.rds` paths, read lazily one at a time;
- one table containing an `ID` column, split into deployments;
- a list of deployment tables or `nautilus_tag` objects.

Factor IDs must drop unused levels before splitting; otherwise removed animals reappear as empty phantom
deployments. File and in-memory paths must receive equivalent validation.

The standard output contract is:

- `return.data = TRUE`: a named list keyed by deployment ID;
- `return.data = FALSE`: `output.dir` is required and written paths are returned invisibly;
- `output.dir = NULL`: do not save;
- non-`NULL` `output.dir`: the directory must already exist; never create it silently;
- skipped deployments do not appear as `NULL` holes in the returned collection.

The filename primitive writes `<id><output.suffix>.rds`. Do not mix successive pipeline stages in one
directory unless filenames cannot collide and downstream selection is deliberately constrained. A tutorial
should normally give every stage its own directory and feed exactly that stage into the next.

A fault local to one deployment should normally record a skip, emit a grouped warning, and continue the
batch. It must not silently disappear or abort unrelated deployments. Every deployment, including a skipped
one, should receive a labelled verbose block. Reserve immediate aborts for invalid call-level arguments,
unusable shared configuration, or a request whose output would be scientifically meaningless for every
input.

The shared exclusions CSV is current state, not immutable history. Each pipeline stage replaces its own
rows on rerun, and `summarizeTagData()` uses the combined file to retain excluded deployments in the cohort
roster. Pass the same file through all exclusion-producing stages.

## 5. Main processing pipeline

The canonical order is:

1. **Validate deployment metadata** with `metadataColumns()` and `checkDeploymentMetadata()`. Data-quality
   problems are reported in the resulting `nautilus_deployments` object; an invalid QC stamp is rejected by
   import.
2. **Ingest the primary record** with `importTagData()`, or construct an already parsed table with
   `buildTagData()`.
3. **Trim the on-animal window** with `filterDeploymentData()`.
4. **Regularise timestamps** with `regularizeTimeSeries()` before algorithms that assume a fixed interval.
5. **Assess structural integrity** with `checkSensorIntegrity()`, then transient anomalies with
   `checkSensorQuality()`. Both are report-first workflows; applying changes is explicit.
6. **Screen position fixes**, where appropriate, with `filterLocations()`. Thresholds are species- and
   study-specific and therefore opt-in.
7. **Resolve the sensor frame** with `checkTagMapping()`, `consensusAxisMapping()`, optional
   `reviewTagMapping()`, and `applyAxisMapping()`.
8. **Estimate magnetometer calibration** with `calibrateMagnetometer()`. This stores a proposal without
   changing raw magnetometer columns.
9. **Derive analysis channels** with `processTagData()`. This applies a trusted compatible calibration,
   computes metrics at native rate, and only then optionally downsamples.
10. **Convert paddle frequency to speed**, when needed, with `calculatePaddleSpeed()`.

Optional downstream branches are independent:

- summaries and figures: `summarizeTagData()`, `processingSummary()`, and plotting functions;
- diving: `detectDives()`, `diveMetrics()`, and dive plots;
- behaviour: `calculateTailBeats()`, `extractFeatures()`, and `getDielPhase()`;
- tracks: `reconstructTrack()`, `crossValidateTrack()`, `trackMetrics()`, maps, and SSM export;
- video: metadata extraction, filtering, annotation, axis-review clips, overlay rendering, and re-encoding.

## 6. Ingestion architecture and API considerations

`importTagData()` is the public file-oriented front door. `buildTagData()` is the public escape hatch for
data already in R. Format-specific and ancillary readers are internal implementation details.

Primary readers currently support:

- CATS/CEiiA multi-sensor CSV exports;
- Little Leonardo acceleration files with optional depth/temperature files. These loggers have no clock, so
  metadata must supply `data_start`.

`format = "cats"` remains the compatibility default. `format = "little_leonardo"` is explicit. With
`format = "auto"`, detection is per deployment and must be conservative: exactly one confirmed reader is
required. Ambiguity or recognisable-but-unidentifiable data is a visible deployment failure; a folder with
genuinely no primary data is a quiet skip. A metadata `tag_format` value takes precedence for that deployment.
Automatic detection uses built-in mappings only.

`buildTagData()` applies no unit conversion, calibration, or axis rotation. Input channels must already use
canonical units and are still in the recorded tag frame. It accepts a POSIXct timestamp or synthesises one
from a start time and sampling rate. It requires at least one recognised sensor channel; `processTagData()`
has stronger downstream requirements, including depth.

Ancillary input is orthogonal to primary readers. `read_wc()` creates lightweight typed records and the
internal `attachAncillary()` aligns and stores them. Sparse positions/events remain in metadata at their own
cadence. A continuous ancillary channel may be interpolated onto the primary grid only when downstream code
requires it. Do not expose `attachAncillary()` or format readers without an explicit API decision, public
documentation, tests, and a stable user-facing ancillary-object contract.

## 7. Scientific and analytical invariants

### Sensor frames and axis mapping

Imported IMU values remain in the raw tag frame until `applyAxisMapping()`. Orientation or directional
metrics computed before mapping do not describe the animal frame.

Axis transforms are sensor-family-specific signed permutations. Acceleration and magnetometer are polar
vectors. Angular velocity is an axial vector, so a polar mapping matrix `M` induces the gyroscope transform
`det(M) * M`. Applying `M` directly to gyroscope data under a reflection is wrong. Reflections can be valid
mounting conventions and must not automatically be treated as errors.

Accelerometer evidence may derive a gyroscope map when the devices are co-oriented, but magnetometer axes
remain independent unless explicitly supported. Accelerometer/gyroscope co-registration validates the
result. Consensus may fill an ambiguity only when a physical hardware group is consistent; it must never
override decisive deployment-level evidence. Unknown grouping identifiers isolate deployments rather than
pooling unrelated hardware.

Mapping metadata records the net transform so reapplication composes correctly and does not silently
double-transform data.

### Magnetometer and heading

Calibration estimation and application are separate. `calibrateMagnetometer()` stores `proposed` parameters;
`processTagData()` decides whether a stored proposal is trusted and compatible with the exact mapped frame.
An applied calibration is idempotent. Never apply source-side calibration constants again: those sidecars are
provenance describing what firmware/export software already did.

Free-swimming animals often sample a near-horizontal band rather than a sphere. A full ellipsoid can then be
underdetermined. The implemented fallback is an explicit hard-iron-only correction with coverage and IGRF
checks, not a falsely confident three-dimensional fit. Preserve explicit status and confidence values; do
not promote a weak result silently.

Magnetometer trust and heading reference answer different questions. A calibrated compass can still be
magnetic rather than geographic. Turning angles and other rotation-invariant differences tolerate a constant
declination offset; absolute bearings and dead-reckoned tracks do not. Downstream code must warn or decline
where an absolute direction is required and the reference is unsuitable or unknown.

### Sampling, filtering, and derived metrics

Derive metrics at original/native rate before downsampling. This applies to orientation, DBA, jerk, vertical
velocity, paddle frequency, and other frequency-sensitive measures. Downsampling is an output operation, not
a shortcut around the scientific calculation.

Depth drift correction may use smoothed depth and surface evidence internally, but the stored depth channel
is the drift-corrected signal rather than a heavily smoothed replacement. Smoothing windows are expressed in
seconds and converted using the sampling rate. Negative zero is a display concern; do not clamp meaningful
negative physical values merely to improve formatting.

Known hazard: `processTagData()` and `filterDeploymentData()` currently estimate rate as samples per populated
whole second and round it. This cannot represent a rate below 1 Hz: any slower regular series reports 1 Hz.
The result affects filters, windows, jerk, vertical velocity, orientation integration, warnings, and metadata.
Do not make a local one-line replacement. A fix must use a gap-robust interval estimator, retain numeric
fractional rates, define what sub-1-Hz operations are scientifically valid, warn when windows collapse to one
sample, and demonstrate no change across the existing high-rate fleet.

### Sensor QC

Integrity checks target structural/hardware faults; quality checks target transient spikes, stalls, and
anomalies. Keep them separate and report-first. A missing channel is not automatically a corrupt deployment:
consult `meta$sensors$excluded` to distinguish an intentional import/QC exclusion from malformed input.

`mag.break` describes a discontinuity in the record and must not by itself delete the complete magnetometer.
A documented paddle wheel without an onboard `paddle_speed` column is normal for most supported hardware.
A present constant paddle channel is a real dead-channel condition.

The transient spike-rate gate is sampling-rate-dependent and has not been validated for subtle high-rate
events. Changes need known-fault data, not only synthetic plausibility.

### Paddle-wheel processing

`processTagData()` extracts native-rate paddle rotation as `paddle_freq` from the raw magnetometer before
calibration/downsampling removes the relevant signal. It does not perform the tag/season conversion to speed.
`calculatePaddleSpeed()` applies or estimates that calibration downstream and writes `paddle_speed`. Existing
meaningful onboard speed should not be overwritten gratuitously.

The paddle detector currently computes `peak.prominence`, but the pipeline does not use it as a quality gate.
Do not wire it into filtering until a known failed/jammed paddle demonstrates the failure mode and validates
an appropriate threshold.

### Dives

Dive detection supports surface, baseline, and upward-excursion references. Phase slopes are physical rates
estimated with centred local least squares and deployment-specific sampling intervals. Descent and ascent
are resolved independently; symmetry between limbs is maintained by a reverse transform. Quantisation and
low sampling rate can make a phase genuinely unresolvable.

A V-shaped dive may legitimately have no bottom. Do not manufacture a bottom phase or warn merely because it
is empty. A pause should end a limb only after the animal has arrived at its destination region. Coarse,
undithered depth and multi-excursion/asymmetric dives remain difficult and require scientific validation.

### Locations and reconstructed tracks

Location screening is opt-in. Automatically acquired GPS/Argos fixes may be screened, while curated user,
deployment, and pop-up anchors should not be discarded automatically.

`reconstructTrack()` requires heading rather than fabricating a path. Speed controls scale; heading controls
shape. Corrections can use linear, error-weighted, scale/rotate, or no VPC. Cross-validation is leave-one-fix-
out and reruns reconstruction from processed input using the same control settings; it does not validate a
previously corrected track. Its error combines heading, speed, currents, and fix uncertainty and should be
described as net reconstruction accuracy.

## 8. Coding conventions

- Public function names are camelCase. S3 classes and data columns use snake_case.
- Use "deployment" for a tag record and "animal" only for the biological subject.
- Use "sampling rate" for samples per unit time; reserve "frequency" for periodic signals such as tail beats.
- Use `datetime` for a timestamp column and "timestamp" in prose.
- Distinguish tag, logger, package, deployment, and animal identifiers.
- Prefer British English in prose: analyse, behaviour, standardise, colour.
- Keep scientific/ecological prose direct. State what a setting changes and the limitation it addresses.
- Use existing validation helpers and `.abort()` so argument errors have consistent grammar and no noisy
  call trace.
- Use the shared quiet/normal/detailed `verbose` system. Warnings that affect correctness are not hidden by
  `verbose = 0`.
- Aggregate repeated cohort warnings by finding, while retaining per-deployment evidence.
- Preserve explicit `NA`/unknown states. Do not convert insufficient evidence into a convenient default.
- Keep R source ASCII where practical. Use `\u` escapes inside strings for symbols. Roxygen prose may use
  ordinary UTF-8 where it renders correctly.
- Use `data.table` deliberately: copy caller data before by-reference operations and restore class/metadata
  after transformations that strip attributes.
- Avoid duplicate implementations of numerical or reporting logic. Extend the existing shared helper when
  the contract is genuinely common.

## 9. Roxygen and documentation requirements

Roxygen comments in `R/` are the source of truth for function help. `NAMESPACE` and `man/*.Rd` are generated
artefacts. After changing an exported signature, behaviour, return structure, defaults, classes, or links:

1. update the Roxygen block in the same change;
2. run `roxygen2::roxygenise()` (or `devtools::document()`);
3. inspect every generated diff;
4. run an Rd/package check and resolve Roxygen warnings rather than accepting malformed internal blocks;
5. include generated NAMESPACE/Rd changes in the same commit.

Use Roxygen Markdown. A public page should normally contain, in order: title, concise description, details
with scientific context, complete parameters, return value, related functions, runnable examples, and
`@export` where applicable. Document units, reference frames, defaults, output shape, failure/skip behaviour,
side effects, and optional dependencies. If a function stores rather than applies a result, say so plainly.

Examples should show the common case first, use small deterministic data, and run during `R CMD check` when
possible. Use `\dontrun{}` only for external files, network access, interactive tools, expensive computation,
or a genuinely unavailable dependency. Never use it just to conceal a broken example.

README describes the current public workflow; NEWS records user-visible changes. When an API moves work to a
new stage, update code, help, README, NEWS, workflow figures, vignettes, tutorials, and cross-references
together. Search the repository for the old vocabulary before considering the migration complete.

## 10. Tutorials and vignettes

Tutorials are executable workflows, not illustrative fragments. Keep stage numbering, paths, prose, and API
calls synchronized. For a disk-backed tutorial:

- state which directories the user must create;
- write each stage to a distinct directory;
- read the immediately preceding stage, especially when consuming stored calibration or QC metadata;
- avoid unconstrained `list.files()` over a directory containing multiple processing generations;
- pass the same exclusions file throughout;
- make optional camera, map, and calibration branches explicit;
- explain species-specific thresholds rather than presenting them as universal defaults;
- preserve warnings about uncertainty, frame of reference, sparse fixes, and insufficient sensor coverage.

Vignettes are shorter conceptual guides and should use generic, runnable examples. Tutorials may refer to the
project's real folder layout and deployment IDs, but must still be internally executable. Any substantive
tutorial edit should be parsed and, where data are available, run end to end. At minimum, verify all variable
definitions, stage paths, filenames, and function signatures mechanically.

## 11. Testing and validation

The minimum loop for a change is:

1. reproduce the defect or scientific failure before changing code;
2. add or identify a focused test that fails for the right reason;
3. implement the smallest coherent fix;
4. run the focused test file;
5. run the complete test suite;
6. regenerate documentation when relevant;
7. build the source package and run `R CMD check`;
8. inspect the diff and working tree before committing.

Tests should cover file and memory input where both are public, batch continuation, metadata/provenance,
return visibility and naming, idempotent reruns, caller-object immutability, and quiet/normal/detailed output
where relevant. Use deterministic synthetic data and explicit tolerances for numerical work. Test scientific
invariants and adversarial boundary cases, not only successful execution.

Optional features must be dependency-gated. A test should skip only when its dependency or platform feature
is genuinely unavailable. Detecting an FFmpeg encoder in `ffmpeg -encoders` does not prove that the encoder
can initialise; hardware paths need a functional probe or a tested software fallback. Likewise,
`parallel::detectCores()` may return `NA` and must not be treated as a known integer.

Run cross-platform CI for macOS, Windows, Ubuntu devel/release, and the configured old-release target. Pay
special attention to:

- locale and UTF-8 behaviour;
- timezones and daylight-saving boundaries;
- floating-point behaviour at circular wrap points;
- CRLF input and portable regular expressions;
- optional-package absence;
- graphics devices and fonts;
- FFmpeg codecs and container tags;
- parallel-core detection;
- R 4.0 compatibility unless the declared minimum changes deliberately.

Scientific changes require evidence proportional to their blast radius. Sampling-rate, filtering,
calibration, axis, orientation, depth, dive, speed, and track changes should be checked against representative
real deployments or established golden outputs in addition to unit tests. Preserve existing fleet results
when the new case is outside the fleet's domain, or explain and review every intended numerical change.

## 12. Known implementation hazards

- Sub-1-Hz sampling is currently mis-estimated as 1 Hz; see Section 7.
- Paddle `peak.prominence` is computed but unused; its value as a QC gate is unverified.
- Batch reporting remains partly repeated across functions, so new early exits can bypass headers, skip
  registers, or summaries. Check all three explicitly.
- Video rendering currently chooses advertised VideoToolbox encoders without proving they can initialise and
  has no automatic libx264/libx265 fallback.
- `.assert_parallel()` and its test assume `parallel::detectCores()` is non-missing.
- Fast-rate transient-spike QC has limited validation.
- `attachAncillary()` is internal despite an older design having considered it public. Treat the current
  NAMESPACE and help pages as authoritative.
- Map coastlines degrade by optional dependency: automatic mode may emit an installation hint; an explicit
  high-resolution request should fail if it cannot be satisfied.
- A `nautilus_tag` can lose class/metadata through ordinary table operations unless `.restoreMeta()` is used.
- Reusing a stage directory can make later `list.files()` calls consume stale or mixed-generation objects.
- An axis transform, calibration, or processing step that is not idempotent can silently corrupt a rerun.
- A quiet early return can make a skipped deployment indistinguishable from successful absence.

When a new confirmed issue is deferred, record it in the repository's issue tracker with evidence, affected
code, impact, and validation needed. Do not recreate a local chronological audit document.

## 13. Commit and push rules

Before editing:

- read this guide, the relevant Roxygen page, implementation, tests, and recent Git history;
- run `git status` and preserve unrelated or user-owned changes;
- determine whether the requested change is behavioural, scientific, documentation-only, or generated output;
- identify the validation required before implementation.

Before committing:

- inspect `git diff`, `git diff --check`, and `git status`;
- ensure no data, plots, model caches, check directories, credentials, or local paths were added;
- confirm generated help matches Roxygen source;
- report every test/check failure honestly, including platform-specific failures;
- keep the commit focused and use an imperative subject that describes the outcome;
- do not bundle unrelated working-tree changes without explicit authorization.

Do not use destructive Git commands, amend published history, rebase shared work, delete branches, or force
push unless the maintainer explicitly requests that exact operation. Do not assume an old branch or stash is
unfinished work; compare it with `main` and its commit message first.

Push only when explicitly requested, after verifying the intended remote and branch and after the agreed
checks pass. Never force-push merely to simplify history. After pushing, verify that the remote branch points
to the intended commit and report any CI result that is available.

## 14. Maintaining this guide

Update this guide in the same commit whenever a durable architecture, API, scientific invariant, validation
rule, or known hazard changes. Remove resolved hazards rather than appending dated completion notes. Put
chronology in NEWS or Git, actionable work in issues, and executable truth in tests.
